Architecture

Ports and adapters: the RAG logic depends only on interfaces it owns. Ollama, PDF libraries and vector databases plug in at the edges, so any of them can be swapped or A/B-tested without touching the pipeline.

The layers, and who may import whom

cli/ · web/Entry points. Parse arguments, call the composition root, print results. No logic.
composition/The only place that turns config into objects (new OllamaEmbedder(...)). Factories and registries live here.
pipeline/ · eval/Orchestration: ingest, index, query, experiments. Talks to ports only.
strategies/ · adapters/Implementations. Strategies are pure algorithms (chunkers, BM25, RRF). Adapters talk to the outside world (Ollama, pdf.js, files).
core/Domain types and port interfaces. Imports nothing from the project except itself, and no third-party runtime packages.

Dependencies point downwards only. core never imports anything above it; strategies and adapters never import each other; only composition knows concrete classes. A dependency-cruiser rule in CI enforces this (RAG-005).

The ports (interfaces) to write first

These live in src/core/ports/. Every implementation on the board implements one of them. Write and review the interface before asking an AI to write any implementation.

// src/core/ports/document-loader.ts
export interface DocumentLoader {
  readonly name: string;
  load(filePath: string): Promise<ParsedDocument>;
}

// src/core/ports/chunker.ts
export interface Chunker {
  readonly name: string;                 // "fixed-size", "recursive", ...
  chunk(doc: ParsedDocument): Promise<Chunk[]>;
}

// src/core/ports/embedder.ts
export type EmbedKind = "query" | "document";
export interface Embedder {
  readonly modelId: string;              // "ollama:all-minilm"
  readonly dimensions: number;
  embed(texts: readonly string[], kind: EmbedKind): Promise<Float32Array[]>;
}

// src/core/ports/vector-store.ts
export interface VectorStore {
  upsert(records: readonly VectorRecord[]): Promise<void>;
  search(query: Float32Array, k: number, filter?: MetadataFilter): Promise<ScoredId[]>;
  delete(ids: readonly string[]): Promise<void>;
  count(): Promise<number>;
}

// src/core/ports/retriever.ts
export interface Retriever {
  readonly name: string;
  retrieve(query: Query, k: number): Promise<ScoredChunk[]>;
}

// src/core/ports/reranker.ts
export interface Reranker {
  readonly name: string;
  rerank(query: Query, candidates: readonly ScoredChunk[], topN: number): Promise<ScoredChunk[]>;
}

// src/core/ports/llm-provider.ts
export interface LlmProvider {
  readonly name: string;
  chat(request: ChatRequest, signal?: AbortSignal): AsyncIterable<ChatDelta>;
}

// src/core/ports/context-assembler.ts
export interface ContextAssembler {
  assemble(query: Query, chunks: readonly ScoredChunk[]): AssembledPrompt;
}

Configuration and feature flags

Every experiment variant is a config file, validated with zod at startup. Flags are ordinary config values read once, in the composition root. Algorithms never read flags themselves.

// rag.config.json
{
  "ingestion":   { "loader": "pdfjs", "cleaners": ["unicode", "dehyphenate", "headers-footers"] },
  "chunking":    { "strategy": "recursive", "maxTokens": 400, "overlapTokens": 60 },
  "embedding":   { "provider": "ollama", "model": "all-minilm", "batchSize": 32 },
  "vectorStore": { "type": "in-memory", "dir": "data/index" },
  "retrieval":   { "strategy": "hybrid", "k": 5, "fusion": "rrf" },
  "rerank":      { "enabled": false, "strategy": "llm", "candidates": 20 },
  "generation":  { "provider": "ollama", "model": "llama3.2", "contextBudgetTokens": 3000, "ordering": "sandwich" }
}

How A/B testing works in this design

  • Each index is namespaced by what built it: data/index/recursive-400__ollama-all-minilm/. Several variants coexist and are reused across runs.
  • Gold labels are pages and text spans, not chunk ids. A chunk counts as relevant if it overlaps a gold span, so every chunking strategy is scored against the same dataset.
  • Every run is reproducible: results record the config hash, git commit, dataset version and model names.
  • Compare per question, not just averages. Reports show which questions each variant won or lost (RAG-084).

Architecture decision records (ADRs)

Any choice that would be expensive to reverse gets a one-page ADR in docs/adr/: context, options, decision, consequences. Tickets that require one say so. ADRs are reviewed in a PR like code.

Code conventions

The goal is code that a reviewer can predict before opening the file. Consistency matters more than any single rule.

TypeScript rules

  • strict: true and noUncheckedIndexedAccess: true. No any; use unknown and narrow it.
  • Named exports only. Each folder exposes its public API through an index.ts.
  • Validate everything that crosses a boundary (config, Ollama responses, LLM JSON output) with zod. Inside the core, trust the types.
  • Prefer readonly data and pure functions. Math and ranking code (cosine, BM25, RRF, metrics) must have no I/O.
  • Dependencies come in through the constructor. Never create an adapter inside another class.
  • Throw RagError with a stable code and a cause; never throw strings. Log once, where the error is handled.
  • No console.log outside cli/; use the injected Logger.
  • Every public interface and class gets a short TSDoc comment: what it does, and anything surprising.

Testing

Unit (most tests)

Pure logic with hand-computed expected values: chunk boundaries, BM25 scores, RRF order, metric values. Fast, no network.

Contract tests

One shared suite per port, run against every implementation. A new vector store passes the same tests as the in-memory one.

Integration

Real Ollama and real PDFs in tests/integration/. Skipped automatically when Ollama isn't running.

Evaluation

Not pass/fail tests but measurements: run with pnpm eval and compare reports.

Git & PR workflow

One ticket, one branch, one pull request. main is always green and always runnable.

The loop for every ticket

  1. Pick a ticket that is ready (all dependencies done). Move it to In progress on this board.
  2. Branch from an up-to-date main: git switch main && git pull && git switch -c feat/rag-024-recursive-chunker. The ticket drawer shows the exact name.
  3. Commit small and often with conventional commit messages. Each commit should build.
  4. Keep up with main: git fetch && git rebase origin/main, then git push --force-with-lease (never plain --force).
  5. Open a pull request using the template below, link the ticket, and move the card to In review. Paste the PR link into the ticket.
  6. CI must pass: typecheck, lint, tests, dependency rules.
  7. Review. Respond to every comment: fix it, or explain why not. Re-request review after changes.
  8. Squash and merge, delete the branch, move the card to Done.

Pull request rules

  • Small: aim for under 400 changed lines. A large ticket becomes several PRs (interface first, then implementation).
  • One ticket per PR, and the ticket id in the title: RAG-024: Recursive chunker.
  • Open a draft PR early if you want feedback on direction before finishing.
  • Review your own diff first, on GitHub, before requesting review. Most mistakes are visible there.
  • Never merge your own PR without a review, and never merge with failing CI.

Reviewer checklist

Design

Does it implement the port without changing it? Is anything concrete created outside the composition root? Would adding the next strategy require editing this code?

Correctness

Do the tests check real expected values, including edge cases (empty input, one item, exact boundaries)? Do they fail if the logic is broken?

Readability

Could you explain each function to someone else? Are names specific? Is any clever code justified with a comment?

Boundaries

Is external data validated? Are errors typed and handled once? Are secrets kept out of code and logs?

Working with AI on this project

The split of work: AI writes the bodies of individual functions and classes, at most one per prompt, never a whole file. You own the architecture, the interfaces, the file around each piece (imports, exports, wiring), the tests' expected values, and the final judgement in review. You must be able to explain every line you merge.

The one-unit rule. Each prompt asks for one function or one class, nothing more. You write the file skeleton yourself, paste in one generated unit, read it, test it, then ask for the next. It keeps you in charge of the structure and keeps every piece small enough to understand completely.

Who does what

The loop for one ticket

  1. Read the ticket and its port. If the interface doesn't exist yet, write it yourself first.
  2. Write two or three tests with hand-computed answers before generating anything. These are your ground truth.
  3. Write the file skeleton yourself: imports, the exported class or function signatures, and TODOs. Then prompt the AI for one function or one class using the template below. Paste it in, read it, run its tests, and only then ask for the next unit.
  4. Read the generated code line by line. Look for invented APIs, hidden I/O, swallowed errors, any, and code outside the file you asked for.
  5. Run the tests and break them on purpose (change an expected value) to confirm they test something.
  6. Open the PR and fill in the "AI assistance" section honestly.

Rules that keep AI-written code healthy

  • Never merge code you can't explain. If a reviewer asks "why?", "the AI wrote it" is not an answer.
  • Interfaces are frozen during implementation. If the AI wants to change one, stop and decide it yourself (with an ADR if it matters).
  • One function or one class per prompt, never a whole file. Small units are easy to read in full, test on their own and explain in review. If the AI returns more than you asked for, delete the extra and ask again.
  • Check every third-party call against the docs (Ollama API, pdf.js, zod). Invented options and endpoints are the most common AI error.
  • Keep humans on the numbers. Expected values in tests, BM25 and metric formulas are verified by hand.
